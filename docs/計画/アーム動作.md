# アーム動作 計画

## 1. 概要

背面搭載のUnitree D1-T(6軸+グリッパー)を、2026年10月後半のマイルストーン
「アームが動かせる(sim/実機どちらでもよい)」に向けて動かす。実機のD1-Tは
すでに手元にある/10月までに確実に届く見込みのため、**実機優先**で進める。

このマイルストーンの合格基準は「ちゃんと動く(任意姿勢に正確に到達する)」ではなく
「進んでいることが見せられる」こと。したがって模倣学習・フル6軸逆運動学のような
重い実装は不要で、最小の労力で「それっぽく動く」ことを狙う。

**現時点で未確認・要調査の情報が多い節がある**(下記「4. 未確認事項」参照)。
このドキュメントはD1 SDK本体・公式ドキュメント(JS描画のため自動取得できず未確認)
ではなく、Unitree公式製品ページ・コミュニティ実装(GitHub)・他ラボの技術レポート
から間接的に得た情報がベースになっている点に注意。実機・SDKが手元に届いたら
本ドキュメントの記述を実物で検証すること。

## 2. マイルストーン

| # | 内容 | 完了条件 |
|---|------|---------|
| A1 | D1 SDK導入・疎通確認 | D1-Tを接続したPCから、SDK付属サンプル(`arm_zero_control`相当)でゼロ姿勢復帰・feedback受信ができる |
| A2 | 低頻度コマンドでの信頼性確認 | 「4-3. 既知の信頼性リスク」の低頻度パターンで、数分間コマンドを送り続けても無応答化しないことを確認する。ここで問題が出た場合は本ドキュメントの前提(A3以降)を全面的に見直す |
| A3 | 2軸joint-space動作デモ | J1(ベース旋回)ともう1軸(肩/肘のpitch系、候補J2かJ3)を直接関節角度指定でスクリプト動作させ、残り4軸は固定姿勢。実機でそれっぽい動きを確認・撮影 |
| A4(任意) | Gazebo統合(#60) | `d1_550_description`をROS2/gz sim向けに移植し、Go2背面に静的TFで搭載。デモ用途なら必須ではなく、余力があれば着手 |

## 3. 方式の選定

候補として「模倣学習」「フル6軸逆運動学」「直接joint-space制御(2軸)」の3つを検討し、
**直接joint-space制御(2軸)を採用**する。

| 方式 | 工数 | 備考 |
|---|---|---|
| 模倣学習(ACT等) | 大 | テレオペでのデータ収集+学習+推論統合が必要。「見せられればいい」水準には過剰 |
| フル6軸逆運動学 | 中〜大 | 6軸シリアルリンクの閉形式IKはそれなりに複雑。任意姿勢到達が要件でなければ不要 |
| **直接joint-space制御(2軸)** | **小** | J1(yaw)+肩/肘いずれか(pitch)を直接角度指定。IK不要。「ある座標を指す」見た目にしたい場合のみ2リンク平面幾何(atan2程度)で足りる |

残り4軸(グリッパー含む)は中立姿勢に固定する。

### 3-1. sim/実機で実装を使い回す(トランスポート層のみ差し替え)

実機優先が最終目標だが、Gazeboを「見せるためだけの使い捨てデモ」にはしない。関節目標値を
決めるロジック(2軸のスクリプト・タイミング)は**sim/実機で共通の1本**にし、その目標値を
実際に送る先(トランスポート層)だけを差し替える構成にする:

- 共通ロジック: 「この時刻にJ1=θ1、肩/肘=θ2」を決めて`/d1/joint_command`相当のトピックに
  publishするだけのノード。sim版・実機版で完全に同じものを使う
- sim側トランスポート: `/d1/joint_command`を購読し、gz simの関節コントローラ(または
  `joint_state_publisher`)に変換する薄いアダプタ
- 実機側トランスポート: `/d1/joint_command`を購読し、D1 SDKの関節角度コマンドに変換する
  薄いアダプタ(#63で疎通確認したインタフェースを使う)

これにより、Gazeboでの検証(#65のURDF統合+このロジック)がそのまま実機実証(#64)の
本体になり、二度手間にならない。**したがって着手順は「先にGazebo上でロジックを作って
動きを固める→実機は薄いアダプタを差し替えるだけ」にする**(#67の優先順位を参照)。

### 3-2. 将来検討: テレオペリーダーアーム(外部協力者提供予定、2026-09-08)

外部協力者が、D1-T用のテレオペ用リーダーアーム(Dynamixelサーボで人手の関節角度を
読み取り、ボードから角度を送信する装置)を作ってくれる予定があるとの情報を得た。
到着見込みは本情報を得た時点から約2週間後。協力者からは「このリーダーアームで
実際に動かしてみて、どこにナビゲーションが必要かを考えるとよいのでは」という提案も
あった。

これにより、3節で「工数対効果が悪い」として不採用にした**模倣学習(ACT等)**の
主要な障壁(テレオペによるデータ収集手段が無いこと)が解消される可能性があり、
10月マイルストーン以降の発展的な選択肢として6軸の模倣学習が視野に入る。

ただし2週間待つのは現在の着手順に対して遅すぎるため、**優先順位は変更しない**:
引き続き#65→#66→#63→#64の順でGazebo優先で進め、模倣学習はリーダーアームが
実際に届いてから、既存の2軸joint-space計画に追加する形で検討する。届いた時点で
追跡用のissueを起票する。

## 4. D1-Tのコマンド体系(現時点の理解)

### 4-1. ハードウェア仕様

Unitree公式ページより:

- 6軸+グリッパー(7自由度扱い)、6061-T6アルミ、質量2.37kg
- 関節可動域: J1/J4/J6 = ±135°(2.36rad)、J2/J3/J5 = ±90°(1.57rad)
- 速度上限90°/s、17bit エンコーダ(位置精度±0.01°)
- 位置/速度/力の3制御モードに対応、24V/2.5A給電(定格60W・ピーク120W)、200Hz IMU搭載
- 公式SDK提供、ROS/ROS2オープンソース対応と案内あり(詳細は4-4参照)

### 4-2. SDKの位置づけ

D1-T用のSDK(「D1 SDK」)は、Go2本体で使っている`unitree_sdk2`/`unitree_sdk2_python`
(このリポジトリの`external/unitree_ros2`が使っているのと同系統)とは**別物**。
`unitree_sdk2_python`のリポジトリ自体にD1/D1-T関連のサンプルは含まれていない
(2026-08-31時点でWeb調査済み)。D1-T向けの入口は
`https://support.unitree.com/home/en/developer/D1Arm_services`
(中文版: `.../zh/developer/D1Arm_services`)。このページはJS描画のSPAで
自動取得ツールでは本文が読めなかったため、実際のサービス名・メッセージフィールドは
実機到着後にSDKを見て確認する必要がある。

Go2と同様にCycloneDDSベースと見られる(他ラボの実装例で`ChannelFactory`初期化時に
NICを指定する記述があった)。

**(2026-09-08更新)** PR #72(未マージ、`feat/real-robot-driver`)で`external/unitree_sdk2`
(公式`unitreerobotics/unitree_sdk2`)をsubmodule追加し、`docker/driver/d1_sdk/`で
D1サンプル6本をビルドできる状態まで整備済み(4-4参照)。ただし公式`unitree_sdk2`本体
リポジトリにD1固有コードは含まれておらず、D1サンプル自体はD1Arm_servicesページ等
から別途入手したものをそのまま持ち込んだと見られる。

物理接続については、Caltech AMBER Labのレポートで「D1アームはGo2本体とは独立に
Ethernetケーブルで直接PCに接続、DDSの`ChannelFactory`初期化時にNIC名を指定」という
構成が確認できた。同ラボの設定ファイル(`Caltech-AMBER/obelisk_examples`
d1_armブランチ、`d1_control/configs/d1_hardware.yaml`)では
`network_interface_name: enx001cc24ce09a`(USB-Ethernetアダプタ系の命名)と、
Go2本体用とは別NICを割り当てていた。本プロジェクトでGo2本体の`GO2_NIC`と共用できるか
別途USB-Ethernetアダプタが要るかは、実機のポート構成次第で未確定のまま。

### 4-3. 既知の信頼性リスク(重要)

Caltech AMBER Lab(Ames研)が2025年にD1アームをGo2に統合しようとした際の
技術レポートで、以下が報告されている:

- 継続的にコマンドを送り続けると**数分でアームが指令に応答しなくなる**(shaky→無反応)
- 送信頻度を10Hz/100Hzと変えても症状は同様。サーボが過熱する例もあった
- **「一定時間おきに1コマンドだけ送る」パターン(30秒に1回程度)にすると、
  約5分程度は安定して動作した**——常時ストリーミングより低頻度コマンドの方が安定
- Unitreeサポートに問い合わせたところ「D1アーム開発チームが競合に引き抜かれ、
  データも消失した」と回答があり、Unitreeは2025年3月時点でD1の販売を終了している
- 最終的にこのラボは「実機が壊れている」と結論し、別のアーム(Z1、高額)への
  切り替えを検討する事態になった
- **(2026-09-08追加調査)** 同レポートによると、Go2本体からの給電に切り替えても
  同じ症状(サーボ過熱・無応答)が再現したため「外部電源が原因ではない」と切り分けた
  上での個体不良判定。したがってこのリスクは電源系統ではなく個体/設計要因である
  可能性が高い
- **(2026-09-08追加調査)** 低頻度コマンド戦略を裏付ける具体的な実測値も記載あり:
  `arm_zero_control`と`multiple_joint_angle_control`を10回程度切り替えても失敗なし、
  ジョイスティックでの離散コマンド(都度1回送信)方式では約5分間安定動作した

これは1台の不具合報告であり全個体に当てはまるとは限らないが、**コミュニティの
サポート体制が薄いハードウェアである**ことは事実。したがって:

- A2(低頻度コマンドでの信頼性確認)を、複雑な動作を作り込む前に必ず単独で行う
- 常時ストリーミング制御ではなく、**低頻度(30秒に1回程度)の離散コマンド**を
  基本方針にする(A3のデモもこの方針に合わせる)
- 数分以上の連続デモは避け、短時間で完結する動作にする

### 4-4. SDK付属サンプル

**(2026-09-08更新)** PR #72(未マージ、`feat/real-robot-driver`)で`external/unitree_sdk2`を
submodule追加し、`docker/driver/d1_sdk/`にD1 SDKサンプル6本を実際に配置・ビルド済みであることを
確認した。以下は同PRのコード(Issue #63コメント・PRファイル)を根拠にした確定情報。
`initialize_arm.cpp`は同梱されておらず、以下4-1で述べた推測は誤りだった:

- `arm_zero_control.cpp` — アームをゼロ姿勢に戻す1コマンドを送る
- `joint_angle_control.cpp` — 単一関節の目標角度を送る
- `joint_enable_control.cpp` — 有効化/放電を切り替える
- `restore_initial_pose.cpp` — 初期姿勢へ復帰
- `multiple_joint_angle_control.cpp` — 全7サーボ(6軸+グリッパー)の目標角度を
  1コマンドにまとめて送る
- `get_arm_joint_angle.cpp` — feedback受信サンプル

コマンド送信は`rt/arm_Command`トピックに`ArmString_`型(JSON文字列を積んだラッパー、
フィールド`seq`/`address`/`funcode`/`data`)を送る方式。`funcode`の意味:
`1`=単一関節角度、`2`=全関節角度、`5`=有効化/放電、`7`=ゼロ姿勢復帰。

feedbackは`current_servo_angle`(`PubServoInfo_`型、`servo0_data_`〜`servo6_data_`)と
`arm_Feedback`(`ArmString_`型、電源投入状態・有効化状態を含む)の2トピック。

**⚠️ 未解決の矛盾(実機到着後に最優先で検証)**: PR #72の`get_arm_joint_angle.cpp`は
`current_servo_angle`/`arm_Feedback`を**`rt/`無し**で購読している。一方Caltech AMBER Lab
の技術レポート(`2025_SURF_Final_Report.pdf`、4-3参照)は「feedbackトピック名を
`arm_Feedback`から`rt/arm_Feedback`に修正しないと受信できなかった」と明記しており、
PR #72のコードにはこの修正が反映されていない。**このままでは実機でfeedbackが
受信できない可能性が高い**。`current_servo_angle`側に`rt/`が必要かはレポートに
記載がなく未確認。実機到着後、まずここを最初に確認すること(A1の一部)。

### 4-5. URDF

Unitree公式(と見られる)CDNから`d1_550_description`パッケージを取得済み
(`https://oss-global-cdn.unitree.com/static/9b20252a26374d50aa369532657d0143.zip`)。
中身を確認したところ、D1-Tの公称スペックと一致する構成だった:

- Joint1/4/6: revolute、可動域±2.36rad(≈±135°)
- Joint2/3/5: revolute、可動域±1.57rad(≈±90°)
- Joint_L/Joint_R: prismatic(グリッパー、各0〜0.033m)
- STLメッシュ・慣性パラメータ込み(SolidWorks URDF Exporter出力)

ただし**ROS1(catkin)+Gazebo Classic向け**にパッケージされており
(`package.xml`がcatkin、`launch/gazebo.launch`が`gazebo_ros`のclassic API)、
このリポジトリのROS2 Humble/gz simでそのまま使うには変換が要る
(ament_cmake化・xacro/SDF化・spawn launchの書き換え。作業自体は定型的)。

Caltech AMBER Labのレポートでも同じ「D1 SDK付属のURDF」を使っており、
そちらでは**円周率が`3.14`/`1.57`と粗く丸められていて逆運動学計算に支障が出た点、
2つの関節の回転軸が実機と食い違っていた点**を修正して使ったと記録されている。
今回取得したURDFも同様の粗い値になっている可能性が高いので、**実機到着後に
関節の回転方向を目視で照合してから信用する**こと(今回の用途はjoint-space直接指定
で精密なIKを解かないため実害は小さいが、A4でGazebo統合する場合は要確認)。

**(2026-09-08追加調査)** Caltechレポートで実際に行った修正内容が確認できた:
円周率を`3.14`→`3.1415926535`、`1.57`→`1.57079632679`に置換、および2軸の回転軸を
実機に合わせて修正(具体的にどの2軸かはレポートに記載なし)。今回入手したURDFと
完全同一かは不明だが、同種の問題が実在することの裏付けが取れた。GitHub上に代替・
修正版URDFは見つからなかった(§5参照)ため、この修正は自分たちで実機と照合して
適用する以外に近道はない。

## 5. 未確認事項(2026-09-08時点)

**(2026-09-08追加調査で判定を更新)** 実機到着前に調べられる範囲は洗った。以下は
「解消/部分解消」と「実機必須で未解消」に分けて記載する。根拠・出典は各項目内、
出典一覧は§6参照。

### 解消 / 部分解消

- D1 SDKの正式名称・入手方法 → **ほぼ解消**。PR #72(未マージ)で
  `external/unitree_sdk2`をsubmodule追加、`docker/driver/d1_sdk/`にサンプル6本を
  配置・ビルド可能な状態(4-2参照)
- 実際のDDSトピック名・メッセージ型・フィールド名 → **部分解消、かつ矛盾を発見**。
  コマンドは`rt/arm_Command`(`ArmString_`型)、feedbackは`current_servo_angle`
  (`PubServoInfo_`型)と`arm_Feedback`(`ArmString_`型)。ただしPR #72のコードは
  feedbackを`rt/`無しで購読しており、Caltechレポートの「`rt/arm_Feedback`に
  修正しないと受信できない」という知見と矛盾している(4-4参照)。**実機到着後、
  最優先でここを検証・修正すること**
- D1-TとPCの物理接続方法 → **部分解消**。Ethernet直結+DDSのNIC指定は確実。
  Caltechの実装ではGo2本体用とは別のUSB-EthernetアダプタNICを割り当てていた
  (4-2参照)。本プロジェクトでGo2本体の`GO2_NIC`と共用できるかは実機のポート
  構成次第で未確定
- OSS調査の継続 → **一定解消**。`unitreerobotics/unitree_ros`issue #116は
  2025-01-17作成以降無回答のまま(公式URDF/xacro提供は期待薄と判断)。
  `chen37058/Grasp-with-the-Unitree-D1`は動作デモのみでURDF同梱なし。
  `Caltech-AMBER/obelisk_examples`(d1_armブランチ)が最も動作実績のある
  コード資産だが、こちらにもURDFは同梱されていない。代替・修正版URDFは
  見つからず、Caltechレポート記載の修正(円周率精緻化+2軸修正、4-5参照)を
  自分たちで実機と照合する以外に近道はない
