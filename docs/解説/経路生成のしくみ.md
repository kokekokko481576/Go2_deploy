# 経路生成のしくみ(やさしい解説)

対象読者: 経路計画(グラフ探索・コストマップ)に馴染みがない人向け。
`straight_line_planner`・`go2_path_planning`が実際に何をしているか、なぜそう作ってあるかを
専門用語をできるだけ噛み砕いて説明する。実装の詳細は各パッケージの README
(`ros2_ws/src/straight_line_planner/README.md`・`ros2_ws/src/go2_path_planning/README.md`)を参照。

## 1. そもそも何がしたいのか

自己位置推定で「今どこにいるか」が分かったら、次は「目的地までどう進むか」を決めたい。
これが経路生成の仕事で、答えは**「今の位置から目的地まで、通ってよい点を連ねた
折れ線(`nav_msgs/Path`)」**を1本作ること。この折れ線を経路追従(`go2_path_following`)が
実際に辿って走る。

経路生成そのものは「行き先を決める」のであって「実際にどう体を動かすか」は考えない
(そこは経路追従の仕事)。地図の上でペンを引くだけ、というイメージに近い。

## 2. なぜ最初から本格的な探索をしないのか

このプロジェクトの経路生成は、**あえて2段階**で作ってある。

### 2-1. 第1段階: 直線を引くだけ(生M1) = `straight_line_planner`

一番簡単な経路の引き方は「今いる場所とゴールを直線で結ぶ」。障害物があろうがなかろうが
気にせず、まっすぐ線を引いて、一定間隔(既定0.1m)で点を打つだけ。

- 良い点: 実装が数十行で済み、バグりようがない。経路生成より下流(経路追従・
  自己位置推定とのTF連携)が正しく配線できているかを、経路生成側の複雑さに
  惑わされずに確認できる
- 悪い点: 障害物があっても避けない。実運用では使えない、あくまで**土台の配線確認用**

### 2-2. 第2段階: コストマップの上で探索する(生M2) = `go2_path_planning`

実運用に近づけるには、「地図のどこが通れて、どこが危ないか」を数値化した
**コストマップ**を用意し、その上で「一番コストの低い道」を探す必要がある。

- **コストマップ**: 地図を細かいマス目(既定5cmグリッド)に切り、各マスに
  「ここを通る際のコスト(通りやすさ)」を持たせたもの。今の構成は3層:
  - **static_layer**: あらかじめ持っている地図(壁など既知の障害物)をそのまま
    コストとして焼き込む層
  - **obstacle_layer**: 顎LiDARのライブスキャンをその場でコストマップに書き込む層。
    地図には無いが今まさに見えている障害物(人が置いた台車等)もここで拾える
    (生M3、Issue #18で追加済み)
  - **inflation_layer**: 障害物の周りに「近づくほどコストが上がる」ぼかしを掛ける層。
    ロボットの図体(footprint)が壁にめり込まないための安全マージン
- **探索(NavFn、ダイクストラ法)**: コストマップができたら、「現在地からゴールまで、
  通過コストの合計が一番小さい道」をグラフ探索で求める。今の既定はダイクストラ法
  (`use_astar: false`)。A*(ゴール方向を優先して探索を絞る改良版)への切り替えは
  設定1つでできるが、まずは素直なダイクストラ法を基準値として確立する方針
  (今後の比較用にA*・MPPI系との比較は後段の課題)

> **深追い注意**: 「ダイクストラ法とA\*の違い」「コストマップのレイヤーをどう合成するか」
> 「膨張半径・コスト減衰率をどう決めるか」を突き詰めると、グラフ探索アルゴリズムの
> 計算量理論やコストマップ設計のノウハウという専門領域に入っていく。動かす・使う分には
> 「壁に近いほど危険度が上がる地図の上で、一番安全で短い道を自動で選んでいる」程度の
> 理解で十分。ちゃんと追いたくなったらNav2公式ドキュメントの`Costmap2D`・`NavFn`の解説が
> 定番の入り口。

### 2-3. まとめ図

```
生M1: 現在地 ---直線で結ぶだけ(障害物無視)---> ゴール          [straight_line_planner]
生M2: 現在地 --コストマップ上でダイクストラ法探索(障害物回避)--> ゴール  [go2_path_planning]
```

役割分担というより「段階的な差し替え」。生M1は配線確認用の土台、生M2で初めて
障害物を避けた実用的な経路になる。

## 3. 生M1と生M2、実際どちらが動いているか

`straight_line_planner`(生M1)と`go2_path_planning`(生M2)は、**購読するトピック
(`goal_pose`)・配信するトピック(`plan`)・その型・QoSまで完全に揃えて**作られている。
これは「中身(直線かグリッド探索か)をどう変えても下流のI/Fは変えずに済む」ようにする
意図的な設計で、当初(`bt_navigator`導入前)は「どちらのノードを起動するか」だけで
生M1↔生M2を切り替えられた。

```
goal_pose(PoseStamped)
    │
    ▼
[ straight_line_planner  または  go2_path_planning ]  ← どちらか一方を起動
    │
    ▼
plan(Path, QoS: RELIABLE/TRANSIENT_LOCAL) ── 経路追従へ
```

ただしIssue #50で経路追従側に`nav2_bt_navigator`を導入した後は、BTが標準の
`ComputePathToPose`アクションを`planner_server`(生M2の中身、NavFn)へ直接投げる構成に
変わっている。`straight_line_planner`はこのアクションを実装していないため`bt_navigator`
の経路には乗らず、**現在は経路生成は常に生M2(`go2_path_planning`のグリッド探索)**を
使う。`straight_line_planner`自体は生M1の実装・配線確認用の最小プランナとしてリポジトリに
残っている。

## 4. このリポジトリでの実装との対応

| 概念 | 実際のノード・トピック |
|------|------------------------|
| 直線経路(生M1、現在は`bt_navigator`の経路には乗らない) | `straight_line_planner_node` → `plan` |
| コストマップ上の探索(生M2・本体、現在の既定経路) | `nav2_planner`の`planner_server`(NavFnプラグイン`GridBased`) |
| goal→探索アクション呼び出し | `nav2_bt_navigator`のBT内`ComputePathToPose`ノード → `compute_path_to_pose`アクション |
| 地図(static_layerの元) | `nav2_map_server` → `/go2_localization/map` |
| 障害物からの安全マージン | `inflation_layer`(`inflation_radius: 0.45`) |

## 5. 実際どうやって開発しているか(探索アルゴリズムは自作していない)

自己位置推定と同じ方針で、**グラフ探索アルゴリズムそのものは自分たちで書いていない**。

1. **既存パッケージをそのまま使う**: コストマップは`nav2_costmap_2d`、探索本体は
   `nav2_navfn_planner`(NavFn、ダイクストラ法/A\*)——どちらもNav2で何年も使われてきた
   既製品。グラフ探索やコストの合成を自分で実装することはしていない
2. **自分たちが書いたのはyamlの設定だけ**: `planner_server.yaml`で
   「このロボットの図体(footprint)・どの地図を使うか・膨張半径をいくつにするか」を
   埋める作業。探索アルゴリズム自体を発明する部分はゼロ
3. **`straight_line_planner`だけは中身も自作**だが、これも「2点を直線で結ぶ」という
   ごく単純な幾何計算であり、土台の配線確認用と割り切っている

つまりここでも実態は「既製の探索エンジンを、Go2のfootprint・地図に合わせて設定し、
アクション呼び出しの配線をするだけ」。独自性を出すべきなのは「船内部材への正対姿勢を
ゴールとしてどう表現するか」「跨ぎ判断のためのタグ付きPath拡張(生M5)」といった、
Nav2の既製品が想定していないGo2固有の部分。

## 6. 今わかっている限界・今後の課題

- **障害物ができた場合の再計画は`bt_navigator`のBTで解決済み**: obstacle_layer
  (生M3、Issue #18)で地図にない障害物(人が置いた台車等)がコストマップに反映され、
  BT(`go2_bt_plugins`)は`RateController`で`ComputePathToPose`を約1Hzで自動的に
  呼び直す(Nav2標準テンプレート由来)。当初計画にあった「経路無効化時のみ再計画」
  ほど選り好みはしないが、Path追従中に新たに現れた障害物にも1Hz程度で追従して
  再計画できている
- **平地専用**: 現状のコストマップは2D(平面)で、防撓材などの段差・跨ぎ対象物を
  「高さ」で区別できない。2.5D標高マップ化(生M4)・跨ぎ判断ロジック(生M5)は今後の課題
- **障害物内ゴールへの対応が弱い**: ゴールが障害物(膨張込み)の中や地図外にあると
  計画結果が空になり、経路が出ない。ゴール位置の妥当性チェックは呼び出し側の責任
- **ダイクストラ法とA\*・MPPI系との比較は未実施**: まずは素直なダイクストラ法を
  基準値として確立した段階で、他手法との比較検証はこれから
