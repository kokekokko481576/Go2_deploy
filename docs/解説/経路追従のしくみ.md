# 経路追従のしくみ(やさしい解説)

対象読者: 局所プランナ(DWB等)に馴染みがない人向け。`go2_path_following`・
`cmd_vel_safety`が実際に何をしているか、なぜそう作ってあるかを専門用語をできるだけ
噛み砕いて説明する。実装の詳細は`ros2_ws/src/go2_path_following/README.md`・
`ros2_ws/src/cmd_vel_safety/README.md`を参照。

## 1. そもそも何がしたいのか

経路生成が「地図の上に引いた折れ線(`Path`)」を渡してくれても、ロボットはそれを
そのまま歩けるわけではない。折れ線はただの点の列であって、「今この瞬間、前にどれだけ
・横にどれだけ・どれだけ旋回する速度で歩けばその線に乗れるか」という**具体的な速度指令
(`cmd_vel`)**に変換して初めて体が動く。この変換を作り続けるのが経路追従の仕事。

しかも1回変換して終わりではなく、ロボットは歩くたびに少しずつ線からズレるので、
**現在位置とPathを見比べて速度指令を出す→少し進む→また見比べる**、を毎秒何十回も
繰り返し続ける必要がある。

## 2. PathをFollowPathへつなぐ橋渡しはどう変わってきたか

Nav2の本来の使い方は、`bt_navigator`という司令塔が「経路を計画し直せ」「ダメなら
その場で回転してリカバリしろ」といった一連の判断をビヘイビアツリー(BT)で行い、
その一部として局所プランナ(`controller_server`)に「このPathに沿って進め」と
指示を出す、という構成になっている。

このプロジェクトも当初(追M2、平地の経路追従)は、あえて`bt_navigator`を導入せず、
**「経路生成が出したPathを、そのままcontroller_serverに渡して追従させてみる」**
という最小構成にとどめていた。理由は、まず「Path→速度指令→実際に歩く」という
一番肝心な変換パイプラインが正しく動くかを、BTの複雑さ抜きに確認したいため。
`bt_navigator`が本来やる「PathをFollowPathアクションのゴールとして送る」仕事は、
自作の小さな橋渡しノード`plan_follower`が代わりに行っていた。

その後、追M3(Issue #23)で接触検知→リカバリ(その場回転・後退・再計画要求)の
判断ロジックを`plan_follower`に条件分岐・タイマー・リトライ状態として積んでいった
結果、そのオーケストレーション自体をBTに任せた方が素直になったため、Issue #50で
`nav2_bt_navigator`を導入した。`plan_follower`(と経路生成側の`plan_requester`)は削除し、
`goal_pose`を`NavigateToPose`アクションへ変換するだけの薄い橋渡しノード
`goal_pose_bridge`に置き換えている。経路計画(`ComputePathToPose`)・追従(`FollowPath`)・
リカバリの判断はすべてBT側(`go2_bt_plugins`のXML + `bt_navigator`/`behavior_server`)に
移り、接触検知(`collision_detector`)が`/collision_detected`を発行すると、BTの
`IsCollisionDetected`条件ノードがそれを検知して追従中の`FollowPath`を即座にキャンセルし、
その場回転(Spin)→待機(Wait)→後退(BackUp)の順でリカバリを試す構成になっている。

## 3. DWB(局所プランナ)は何をしているのか

`controller_server`の中身(既定はDWB、`dwb_core::DWBLocalPlanner`)がやっていることは、
一言で言うと**「これから0.1秒後・0.2秒後…と少し先まで進んだ場合の候補ルートをたくさん
思い浮かべ、一番良さそうなものを選ぶ」**という判断を、毎周期(既定20Hz)繰り返すこと。

具体的な手順:

1. **候補となる速度の組み合わせをたくさん作る**(`vx_samples`・`vy_samples`・
   `vtheta_samples`個ずつ、前後速度×旋回速度の格子)。例えば「前0.1m/sで旋回0.2rad/s」
   「前0.15m/sで旋回0.0rad/s」…といった組み合わせを何百通りも用意する
2. **各候補について「その速度で`sim_time`(既定1.7)秒進んだら、どこに着地するか」を
   仮想的に計算する**(実際には動かさず、計算上シミュレートするだけ)
3. **着地点を複数の評価関数(critics)で採点する**。今の構成では7種類の評価軸を
   組み合わせている:

   | critic | 何を評価するか |
   |--------|----------------|
   | `PathAlign` | 経路の向きに姿勢が沿っているか |
   | `PathDist` | 経路からどれだけ離れているか |
   | `GoalAlign` | ゴールの向きに姿勢が沿っているか |
   | `GoalDist` | ゴールにどれだけ近づけるか |
   | `RotateToGoal` | ゴール付近で正しい向きに旋回できているか |
   | `Oscillation` | 前後・左右にふらついていないか(同じ場所で往復する挙動を抑える) |
   | `BaseObstacle` | 障害物に近づきすぎていないか |

   各criticには重み(`scale`)があり、点数の合計が一番高い候補を「今この瞬間に
   出すべき速度指令」として選ぶ
4. これを`cmd_vel`として配信し、次の周期(1/20秒後)でまた1からやり直す

> **深追い注意**: 「軌道サンプリングの密度をどう決めるか」「criticの重み付けを
> どうチューニングするか」「DWBとTEB・MPPIといった他の局所プランナ方式の違い」を
> 突き詰めると、局所軌道計画(local trajectory rollout)というそれ自体が研究領域の
> 沼につながっている。動かす・使う分には「候補ルートを何百通りも試算して、
> 経路に沿いつつ障害物を避けられる一番良さそうな速度を毎秒何十回も選び直している」
> 程度の理解で十分。ちゃんと追いたくなったらNav2公式ドキュメントの`DWB`アーキテクチャ
> 解説、あるいはFox/Burgard/ThrunのDynamic Window Approach原論文が定番の入り口。

## 4. なぜ`cmd_vel_safety`を間に挟むのか

DWBが出す`cmd_vel`は「経路に一番忠実な速度」であって、「実機にとって安全な速度」を
保証してはいない。設定ミスや別経路(テレオペ等)からの指令が、突然大きな速度・
急な加速度で来ることもありうる。そこで最終段に**安全フィルタ**を1枚挟んでいる:

- **速度クランプ**: 前後・左右・旋回それぞれに上限速度を設定し、それを超えないようにする
- **加速度レート制限**: 直前の指令からの変化量を制限し、急加速・急停止を抑える
- **ウォッチドッグ**: 指令が一定時間(既定0.5秒)途絶えたら自動でゼロ指令を出し続けて
  止まる(上位ノードがクラッシュした・通信が切れた、といった異常時の安全網)

DWB(や将来のテレオペ・他プランナ)がどんな速度を出してきても、**この1枚を必ず
通してから実機/Gazeboに渡す**ことで、上流の実装ミスがそのままロボットの暴走に
つながらないようにしている。

## 5. まとめ図(データフロー)

```
goal_pose(PoseStamped)
    │
    ▼
goal_pose_bridge ──NavigateToPoseアクション──▶ nav2_bt_navigator(BT)
                                                     │ ComputePathToPose → FollowPath
                                                     │ (接触検知でFollowPathを即キャンセルしリカバリへ)
                                                     ▼
                                            controller_server(DWB, FollowPathアクション)
                                                     │
                                       現在位置(TF)と見比べて評価・選定
                                                     ▼
                                           cmd_vel_raw(生の速度指令)
                                                     ▼
                                              cmd_vel_safety
                                 (速度クランプ + 加速度制限 + ウォッチドッグ)
                                                     ▼
                                           cmd_vel(最終駆動指令)
                                                     ▼
                                   歩容制御(Gazebo歩容 / 実機Sport Mode API)
```

## 6. このリポジトリでの実装との対応

| 概念 | 実際のノード・トピック |
|------|------------------------|
| goal_pose→NavigateToPoseの橋渡し | 自作`goal_pose_bridge` |
| 経路計画・追従・リカバリの判断(BT) | `nav2_bt_navigator` + `go2_bt_plugins`のBT XML・条件ノード(`IsCollisionDetected`) |
| 局所プランナ本体(DWB) | `nav2_controller`の`controller_server`(`FollowPath`プラグイン) |
| 速度・加速度クランプ+ウォッチドッグ | 自作`cmd_vel_safety_node`(`cmd_vel_raw`→`cmd_vel`) |
| 実機への最終変換(Sport Mode API) | 自作`go2_sport_bridge`(`cmd_vel`→`/api/sport/request`のMove) |

## 7. 実際どうやって開発しているか(局所プランナは自作していない)

自己位置推定・経路生成と同じ方針で、**DWBの軌道評価アルゴリズムそのものは
自分たちで書いていない**。

1. **既存パッケージをそのまま使う**: `dwb_core`・`dwb_critics`はNav2で何年も
   使われてきた既製品。軌道のサンプリング・評価・選定ロジックを自分で実装する
   ことはしていない
2. **自分たちが書いたのはyamlの設定 + 橋渡しノード + 小さな安全ロジック**:
   `controller_server.yaml`で「Go2の速度上限・footprint・criticの重み」を
   既存パラメータの意味に沿って埋める作業と、`goal_pose_bridge`(数十行の橋渡し)、
   `go2_bt_plugins`のBT条件ノード(接触検知でFollowPathを止めるだけ)、
   `cmd_vel_safety`(クランプ・レート制限・ウォッチドッグという既知の考え方を
   数十行に落としただけ)。DWBのアルゴリズム自体を発明する部分はゼロ

独自性を出すべきなのは「Go2の脚が苦手な動き(急な横移動・急旋回)を反映した速度上限・
加速度上限の設定」「工場出荷歩容(Sport Mode API)への最終変換」といった、Go2固有の
橋渡し部分。

## 8. 今わかっている限界・今後の課題

- **障害物回避・リカバリは追M3(Issue #23)で実装済み**: local_costmapに
  `obstacle_layer`(顎LiDARのライブスキャン)を追加し、接触検知→BTでのリカバリ
  (その場回転→待機→後退)まで動く。ただし接触1回あたり0.2〜1.0m程度のオドメトリ
  ズレが残ることが確認されており(自M3/#14で評価継続中)、リカバリ自体は動いても
  推定位置の乱れは解消しきっていない
- **DWBとMPPIの比較が未実施**: `controller_server.yaml`にはDWB(`FollowPath`)と
  MPPI(`FollowPathMPPI`)を両方ロードしてあるが、BT XMLは`FollowPath`(DWB)を
  固定で使う構成になっており、比較・選定はIssue #22で今後行う
- **GATE1の定量誤差は自己位置推定の誤差を含んだ値、かつ現状は大半が偽陽性**:
  到達成功率・誤差は「自己位置推定が報告する現在地」を基準に測っているため、
  経路追従の制御精度と自己位置推定の絶対精度が混ざっている(詳しくは
  `自己位置推定のしくみ.md`)。#43でGazebo真値との比較機能を追加したところ、
  GATE1(#36)の推定ベース成功率46%に対し真値ベースは6%しかなく、セッション中に
  自己位置推定がリセットされないまま誤差が蓄積することが主因と判明した(Issue #54、
  対応中)
- **跨ぎスキルへの切り替えは未統合**: 段差・防撓材を跨ぐ動作(Isaac Labで別途学習)への
  切り替えロジックは追M5(Issue #25)でダミースキルから着手予定
